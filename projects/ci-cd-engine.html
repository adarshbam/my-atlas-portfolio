01 · The execution model

A push becomes a dependency graph.

The engine verifies the raw webhook signature before parsing the event, filters the repository and branch, and deduplicates deliveries. The scheduler then starts jobs whose prerequisites have succeeded, with two slots per run.

Each job runs sequential Bash steps in its own temporary directory. Declared artifacts connect dependent jobs. Retries, timeouts and cancellation handle failures, while configured GitHub commit statuses report the pipeline result.

02 · Making execution legible

See the run. Find the failure.

Workflows, without guessing

Browse loaded definitions, inspect configuration, copy a workflow’s webhook URL or trigger a run manually.

Execution, in context

The React Flow graph follows the actual job topology. A job inspector exposes step output, exit codes and execution logs; running work can be cancelled.

History that survives a restart

Runs and logs persist on local disk. The run list supports search and filters, with branch, commit, duration and job progress beside each execution.

Failures worth explaining

Blocked dependencies skip downstream work. Cycles produce diagnostics naming the stuck jobs and their dependencies instead of leaving a run waiting indefinitely.

03 · Before the first push

One engine host. One public ingress.

For a local demonstration, ngrok lets GitHub reach the engine’s webhook listener. The dashboard composes a payload URL for the selected workflow using the configured public base URL.

The engine runs on your host. Deployment destinations, credentials and commands belong to each workflow; ngrok provides ingress rather than deployment hosting.

Complete setup guide ↗

  1. Prepare the host

    Install Node.js 20+, npm, Git, Bash and authenticated ngrok. Install backend and dashboard dependencies. Configure the environment from .env.example, including a matching webhook secret.

  2. Start the engine and dashboard

    Run npm run dev and npm run dashboard:dev. Start the tunnel with npm run tunnel; set its HTTPS origin as PUBLIC_WEBHOOK_BASE_URL.

  3. Connect the repository

    Load a JSON workflow with its own webhook route and branch/repository filters. Add its generated payload URL in GitHub’s webhook settings, choose JSON and push events, enable SSL verification and enter the same secret. Update the base and GitHub setting if the tunnel URL changes.

  4. Run and inspect

    Push a commit or trigger a run from the dashboard. Supply a GitHub token with commit-status write permission for status reporting. Configure actual checkout, test and deployment commands for the target project before relying on the result.

04 · Decisions & boundaries

Small enough to understand.

Bounded concurrency

Two slots per run keep execution predictable. Readiness is reconsidered after the current batch settles, so a newly unblocked job can wait for an independent sibling. The limit is per run, not global.

Local persistence

Disk-backed history avoids an external database for a single-host tool. This is a self-hosted engine, not a distributed worker fleet.

Traceable learning

The project began with structured deployment milestones. My implementation developed the scheduling, concurrency and process lifecycle work into an engine with a visual management layer.

Trust the workflow author

Temporary workspaces separate working files, but commands retain the runner’s OS permissions. They are not container or VM sandboxes. Use trusted workflows and keep management access local or explicitly authenticated.

Keep claims tied to evidence

The supplied screenshots document the interface and captured runs. Features here were checked against current source; no production deployment or fresh full-engine test run was performed for this case study. Pause and the dashboard’s post-MVP extension labels are not presented as implemented capabilities.
